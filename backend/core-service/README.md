## Organization directory and own unit — 2026-10-23

`GET /api/v1/org/staff` accepts optional `keyword` (trimmed, at most 100 characters)
and `activeOnly` (default false), combined with existing departmentId/jobTitle/page/size.
PostgreSQL filters before pagination with stable fullName/staffId ordering. Literal
Vietnamese accent-insensitive search covers names, title labels and unit name/abbreviation;

## Product scope — 2026-10-17

Part of **MediFlow: A Microservices-Based Hospital Information System for Outpatient Care Management**. Core hosts Organization and Patient for outpatient identity, staff and departments, retaining separate data authority.

Canonical [system design](../../docs/plans/01-system-design.md), [contracts](../../docs/plans/03-contracts.md) and [acceptance runbook](../../docs/plans/06-acceptance-runbook.md) define current scope. Existing APIs, feature flags and historical test counts below do not certify full workflow release acceptance.


Core is the single deployment for the Organization and Patient bounded contexts. Their source,
business rules, wire DTOs, migrations, and PostgreSQL stores live in this module while retaining
their separate `com.mediflow.organization` and `com.mediflow.patient` packages. Existing API routes
are served behind `core-service` service discovery.

Organization and Patient use separate datasource URLs, entity managers, transaction managers,
and Flyway locations. Their schemas and data remain separate. Configure
`MEDIFLOW_ORGANIZATION_DB_*`, `MEDIFLOW_PATIENT_DB_*`, and `MEDIFLOW_JWT_SECRET` for a local run.
RabbitMQ and Eureka use the shared MediFlow settings.

Request examples are in `requests/organization.http` and `requests/patient.http`.
The Markdown files in `requests/` retain the original context documentation.

## Automatic persistent local demo data

Core automatically seeds **10 departments, 20 staff, 10 patients and 10 accounts** on startup
with the default profile (no explicit active profile) or `local`. No separate script, existing
ADMIN, or Gateway startup is required for seeding. Gateway uses the resulting Organization
accounts for login. All source data and initial login credentials are in one file:
[demo-seed.json](src/main/resources/demo-seed.json). This is synthetic local development data.

Start the existing development stack from the repository root:

```powershell
docker compose up -d --build postgres rabbitmq eureka-server gateway core-service
```

The initial password for all ten demo accounts is `MediFlowDemo@2026`. Usernames:
`demo.admin`, `demo.manager`, `demo.doctor`, `demo.doctor2`, `demo.nurse`, `demo.lab`,
`demo.pharmacist`, `demo.cashier`, `demo.patient`, `demo.patient2`.
The JSON file maps each account to its role and staff/patient seed key. IDs are generated by
the normal business use cases; patient account references use the actual Patient result IDs.

Each context stores its own seed receipts atomically with its writes. PostgreSQL advisory
transaction locks serialize concurrent seeds. Restarts skip completed seed keys even if you
changed names, identity numbers, departments, account status or passwords. Deleted seeded rows
are not recreated after their receipt has been recorded. Existing natural-key matches can be
adopted on first execution; an account with conflicting role/person linkage stops seeding rather
than reassigning it. Seed counts describe this dataset, not a cap on an already populated DB.
Each context commits independently; a partial startup can safely resume on the next run.
Normal creation use cases preserve validation, password hashing and event/outbox behavior.

Compose keeps these stores in PostgreSQL volume `mediflow-pgdata`; restart and `docker compose down`
preserve them. Do not delete this volume or run `docker compose down -v` to retain your data.
Do not enable the separate first-ADMIN bootstrap below when using this dataset.
To disable demo seeding, set `MEDIFLOW_DEMO_SEED_ENABLED=false` in the Core process/container
environment. Explicit profiles other than `local` (including `prod`, `production`, and packaged
acceptance profiles) do not activate this seeder. Automated module tests disable it unless
explicitly testing the seed configuration.

## Patient identity correction — 2026-10-20

`PUT /api/v1/patients/{id}` accepts optional `soCmnd` for ADMIN/NURSE. Missing/null retains
the current number for existing clients. A supplied number must contain 1–20 characters with
nonblank content and is trimmed before persistence. A number belonging to another patient
returns `409 PATIENT_CMND_DUPLICATE`; retaining the current number is allowed. The patient UUID
and creation time remain unchanged. The existing PostgreSQL unique constraint guards concurrent
assignments; no schema migration or new endpoint/role is introduced. Existing `patient.updated`
event bytes retain their contract and do not include the identity number.

## Organization delivery and staff retries — 2026-10-21

Organization mutations now append their existing event bytes to
`organization_event_outbox` in the Organization transaction. The relay publishes persistent
messages with mandatory routing and publisher confirmation. Delivery remains at least once:
after a crash between broker confirmation and the database commit, consumers may receive the
same stored event ID and payload again. Patient persistence and its outbox remain separate.

The relay runs every 5 seconds by default, with exponential retry delay capped at 300 seconds
and quarantine after 8 failed attempts. Settings are
`mediflow.organization.event-outbox.scheduling-enabled`, `delay-ms`, and `maximum-attempts`.
Monitor PENDING age and QUARANTINED rows in this context's own store. After repairing routing
or broker availability, an operator may reset a reviewed quarantined row to PENDING with
`attempts=0`, `next_attempt_at=CURRENT_TIMESTAMP`, and `last_error=NULL`; preserve its event ID,
payload and routing fields. This recovery does not create another staff record.

`POST /api/v1/org/staff` accepts an optional `Idempotency-Key`. The receipt is scoped to the
authenticated actor and exact create request fields, including null values. First creation returns 201; a matching
retry returns 200 with the original staff ID and Location, plus `Idempotency-Replayed: true`.
Reusing that actor/key for different data returns 409 `STAFF_IDEMPOTENCY_KEY_REUSED`.
Clients must keep the same key across uncertain responses, and use a new key for a new intent.
The Organization StaffForm now follows that rule. Unkeyed legacy clients retain their existing
create semantics; previously created duplicate records require separate reconciliation.

Gateway refresh reads `GET /api/v1/org/accounts/{accountId}/identity` using its own service
identity. Only the Gateway service can call this endpoint. Refresh requires an expiring,
valid refresh token and the current active account identity; stale roles and identity links
are replaced by the current snapshot. An unavailable lookup cannot issue a new access token.

Verification for these changes: `mvn -q -pl backend/core-service -am test` passed **213 Core
tests**, zero failures/errors/skips, with PostgreSQL/RabbitMQ Testcontainers. The first full
run exposed a web-slice fixture missing the new identity use-case mock; the fixture was fixed
and the full command then passed. Gateway's final full suite and separate refund-route
acceptance run passed **1,500 tests** in total, including the exact EXAM refund-due route
role/method/path checks. Organization API/StaffForm focused
frontend tests passed **11 tests**, with typecheck and lint also passing. These are module
and contract results; they do not certify deployed browser or six-application acceptance.


## Account detail and one active account per owner — 2026-10-22

ADMIN can GET `/api/v1/org/accounts/{accountId}` using the existing password-free
`AccountResponse` envelope, with `Cache-Control: no-store`; other roles are denied.
Create-account and update-status request DTOs accept optional `replaceActiveAccount`
(omission means false). The account role and existing identifiers retain their wire names.

Creation and activation serialize by the linked staff/patient using an Organization
transaction-scoped PostgreSQL advisory lock. An existing active account returns 409
`ACCOUNT_OWNER_ACTIVE`, without changing any account. With explicit confirmation=true,
other active accounts become inactive and their credential versions increment in the
same transaction as saving the target. Any failed save/receipt rolls back all changes.
Inactive account history and existing passwords remain intact. This affects login and
refresh; already issued access tokens still follow their existing TTL.

Idempotent creation fingerprints include the confirmation flag in the SHA-256 digest.
Replaying a confirmed receipt returns that original account without deactivating an account
activated later. Historical requests without the flag keep their original fingerprints.
Contract fixtures: `AccountControllerSecurityTest`, `AccountManagementControllerTest`,
`AccountOwnerPolicyTest`, and `OrganizationServiceIntegrationTest`; Gateway role matrix:
`backend/gateway/src/test/resources/route-role-contracts.csv`.

## Staff privacy and account security — 2026-10-22

Human staff GET list/detail responses expose private fields only to ADMIN. Other permitted
roles receive the work directory: staff ID, full name, department, job title, specialization
and active status. Identity number, license, telephone, email and audit timestamps are null.
Both responses use Cache-Control: no-store. Service lookup contracts remain separate.

ADMIN can search `GET /api/v1/org/accounts` using `keyword`, `role`, `active`, `page`, `size`.
Keyword matches a literal username substring; results never contain password hashes.
Human accounts can `PUT /api/v1/org/accounts/me/password` with currentPassword/newPassword.
Successful password commands return HTTP 200 with the standard ApiResponse and data=true.
ADMIN can `PUT /api/v1/org/accounts/{accountId}/password` with newPassword after verifying
the account owner. SYSTEM accounts cannot be reset using this human management endpoint.
There is no email/SMS password recovery provider in this implementation.
Passwords require at least 8 characters and at most 72 UTF-8 bytes; unchanged passwords
are rejected. Password changes increment credential_version in the same locked transaction.
Verify credentials and the Gateway-only identity snapshot include credentialVersion.
Gateway refresh tokens must match the current version, so old refresh tokens stop working
after password changes. Already issued access tokens remain valid until their configured TTL
(default 30 minutes); this does not implement immediate access-token revocation.

### Explicit first administrator for local development

Bootstrap is disabled by default, requires Spring profile `local` and the explicit enabled
property, and skips creation when any ADMIN account already exists (including inactive).
It creates a department, staff with required unique 12-digit identity number, and ADMIN in
one Organization transaction. An advisory lock prevents duplicate concurrent bootstraps.
Do not use this as a production recovery endpoint. After building Core, run in PowerShell
from the repository root with PostgreSQL/RabbitMQ/Eureka available:

```powershell
$env:MEDIFLOW_BOOTSTRAP_ADMIN_ENABLED = "true"
$env:MEDIFLOW_BOOTSTRAP_ADMIN_USERNAME = Read-Host "Admin username"
$env:MEDIFLOW_BOOTSTRAP_ADMIN_FULL_NAME = Read-Host "Full name"
$env:MEDIFLOW_BOOTSTRAP_ADMIN_IDENTITY_NUMBER = Read-Host "12-digit identity number"
$secret = Read-Host "Admin password (8+ characters, max 72 UTF-8 bytes)" -AsSecureString
$env:MEDIFLOW_BOOTSTRAP_ADMIN_PASSWORD = [System.Net.NetworkCredential]::new("", $secret).Password
try {
    java -jar backend/core-service/target/core-service-0.0.1-SNAPSHOT.jar --spring.profiles.active=local
} finally {
    Remove-Item Env:MEDIFLOW_BOOTSTRAP_ADMIN_ENABLED, Env:MEDIFLOW_BOOTSTRAP_ADMIN_USERNAME, Env:MEDIFLOW_BOOTSTRAP_ADMIN_FULL_NAME, Env:MEDIFLOW_BOOTSTRAP_ADMIN_IDENTITY_NUMBER, Env:MEDIFLOW_BOOTSTRAP_ADMIN_PASSWORD -ErrorAction SilentlyContinue
}
```

Stop the existing Core instance before launching another on the same port. This example
starts a local jar; Docker Compose containers do not inherit these host variables automatically.
Subsequent starts need no bootstrap settings. Flyway applies Organization V9 automatically;
deploy updated Core before updated Gateway so both understand credentialVersion.


## Organization detail enrichment — 2026-10-22

Organization Flyway **V11** adds nullable department `description`, `phoneNumber`, `email`
and staff `dateOfBirth`, `gender` (MALE/FEMALE/OTHER), `address`, `hireDate`, `qualification`.
Existing routes and all existing field names remain valid. Human department/staff responses
include the new fields at the top level; service lookup/event contracts are unchanged.

Create/update requests accept an optional **profile** object. Department profile contains
`description`, `phoneNumber`, `email`; staff profile contains the five new staff fields above.
On update, omitted/null profile preserves existing enrichment. An object replaces the entire
profile: omitted members become null, and `{}` clears all new fields. FE always submits the
complete loaded profile, including explicit nullable members. The HTTP examples and DTO contract
tests lock these shapes. No new endpoint is introduced.

Birth dates must be in the past and hire date must follow birth date when both are present.
Description is limited to 2000 characters, address to 255, qualification/email to 100, and
unit phone/extension to 3–30 characters. Non-ADMIN directory responses redact birth date,
gender, address and hire date along with existing personal fields; qualification remains public.
ADMIN and the signed staff owner receive full detail under existing authorization.

ADMINISTRATIVE offices may assign any active employee in that same office as head.
CLINICAL/PARACLINICAL heads must still be active doctors in their own department.
The department form and staff-title update guard follow this rule.

Fresh demo inserts populate enrichment for all 10 departments and 20 employees in
`src/main/resources/demo-seed.json`. Existing master creation receipts still prevent duplicates.
The one-time enrichment described below fills missing new fields on previously tracked demo rows.
Start the updated Core jar normally; Flyway applies V11/V12 to the Organization store automatically.


### One-time enrichment of existing demo masters — 2026-10-22

When the local/default demo runner is enabled, `seedMasters` also completes one enrichment pass
for each previously tracked department/staff seed key. It uses the UUID in
`local_demo_seed_receipt`, never guesses identity from a renamed record. Only the new nullable
profile columns are eligible: department description/phone/email and staff birth date/gender/
address/hire date/qualification. Null or blank text gets the value from the bundled JSON;
nonempty values and all original fields, account credentials/status, and Patient data stay intact.
An edited date that conflicts with the seed's other date is preserved and the incompatible
missing date stays empty. No record is recreated when a tracked row has been deleted.

Flyway V12 adds `local_demo_profile_receipt`. The Organization transaction/advisory lock covers
updates and receipts together, serializing concurrent starts. Failure rolls both back; a later
startup retries. Once a key is completed, replay skips it even if the user later clears fields.
New inserts already contain profile data; newly adopted untracked rows are only marked complete
without enrichment. Changing the JSON later does not rerun this completed enrichment pass.

No manual SQL, database reset, extra script or new API is required. Rebuild/restart Core with
normal demo seed enabled (`MEDIFLOW_DEMO_SEED_ENABLED`, default true in development). Existing
profile exclusions still disable this runner in production/test/acceptance configurations.

Verification: full Core suite **308 tests, 0 failures/errors/skips**, including PostgreSQL
concurrent startup/replay and V12 migration; seven focused backfill tests cover preservation,
clear-after-completion, rollback/retry, untracked adoption, deletion and date conflicts.
